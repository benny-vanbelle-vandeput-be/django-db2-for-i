- **`m2m.add()`, `m2m.set()`, `bulk_create(ignore_conflicts=True)` and `bulk_create(update_conflicts=True)` can raise an error when two jobs insert the same row at the same moment.** Unlike PostgreSQL's `ON CONFLICT`, a `MERGE` first looks for the rows that exist and then inserts the rest. You may see `IntegrityError` (SQL0803, duplicate key), which undoes the whole statement including its rows without a conflict, or possibly `OperationalError` (SQL0913, row in use) if the other job has not committed yet. To handle it, retry the call inside `with transaction.atomic():`, a few times, catching both errors; the other job's row is there once it commits. Known Limitations has the code. **Not verified on IBM i:** the race comes from IBM's `MERGE` documentation, because testing it needs two connections; the `SQL0803` error and the undone statement were tested with one connection.
- `bulk_create(update_conflicts=True)` does not set the primary keys of the objects (a `MERGE` returns no rows). Read the objects again if you need their keys.
- The same key twice in one `bulk_create()` call with conflict handling raises `IntegrityError`.
- `ignore_conflicts` matches only unconditional unique keys: a conflict in a conditional or functional unique constraint raises `IntegrityError`.
