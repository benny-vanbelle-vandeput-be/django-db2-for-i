- `has_select_for_update`, `has_select_for_update_skip_locked`, `has_select_for_update_of`, `select_for_update_of_column`, `supports_select_for_update_with_limit`: `select_for_update()` locks the selected rows until the transaction ends, written `FOR UPDATE ... WITH RS` (a plain `FOR UPDATE` under `*CS` keeps no lock once the rows are fetched), with `skip_locked=True` (`SKIP LOCKED DATA`), `of=(...)` and on a slice. A query with a join is written `WITH RS USE AND KEEP EXCLUSIVE LOCKS`, which locks the rows of every joined table (Db2 for i refuses `FOR UPDATE` with a join). `nowait=True` stays unavailable. Another job's plain read of a locked row waits too and fails with SQL0913 after the table's record wait (Known Limitations). Django's `select_for_update` tests are a supported module.
- `test_db_allows_multiple_connections`: Django's tests may open a second connection to the test library (phase 7, answer 6). PUB400's rule allows up to three for lock and concurrency tests; no test in the supported modules needs more (`basic.test_concurrent_delete_with_save` and `transactions.test_atomic_prevents_queries_in_broken_transaction_after_client_close` now run and pass).
- `UUID4()` (Django 6.1) works where the server has `GENERATE_UUID()` (IBM i 7.5 Db2 PTF Group SF99950 level 8): checked at the first connection, capability `has_generate_uuid`. `db_default=UUID4()` stays off.
